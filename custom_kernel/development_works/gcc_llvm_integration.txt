=====================================================================
GCC & LLVM INTEGRATION AND USAGE
FOR OPERATING SYSTEM / KERNEL DEVELOPMENT
(STABILITY-FIRST, BSD-PLUS DISCIPLINE)
=====================================================================

---------------------------------------------------------------------
SECTION 1 — PURPOSE OF USING GCC AND LLVM TOGETHER
---------------------------------------------------------------------

GCC:
- Primary production compiler
- Conservative and stable code generation
- Excellent ABI stability
- Best support for inline assembly
- Mature support for exotic and legacy architectures
- Preferred for release and long-term support builds

LLVM / Clang:
- Advanced static analysis
- Modern diagnostics and warnings
- Sanitizers for bug detection
- Better tooling (formatting, LSP, analyzers)
- Faster builds in many cases
- Preferred for development, testing, and verification

Rule:
Never replace one with the other.
Use both in parallel for correctness and stability.

---------------------------------------------------------------------
SECTION 2 — INTEGRATION MODEL (RECOMMENDED)
---------------------------------------------------------------------

Single source tree
Multiple toolchains
Build-time selection

Directory layout example:

kernel/
  arch/
  mm/
  sched/
  ipc/
  drivers/
  include/
  toolchains/
    gcc.mk
    llvm.mk
  Makefile

No source-level divergence is allowed.

---------------------------------------------------------------------
SECTION 3 — BUILD SELECTION MECHANISM
---------------------------------------------------------------------

Toolchain is selected at build time.

Examples:
TOOLCHAIN=gcc   → production build
TOOLCHAIN=llvm  → development / analysis build

The kernel source must compile cleanly with BOTH.

---------------------------------------------------------------------
SECTION 4 — GCC USAGE (PRODUCTION / RELEASE)
---------------------------------------------------------------------

Primary usage:
- Shipping kernel binaries
- Long-term stable builds
- Hardware compatibility

Typical GCC kernel flags:
-ffreestanding
-fno-builtin
-fno-pic
-fno-plt
-fno-stack-protector
-fno-strict-aliasing
-fno-omit-frame-pointer
-nostdlib
-Wall
-Wextra
-O2

Key rules:
- No undefined behavior
- No reliance on GNU-only extensions unless isolated
- Inline assembly must be explicit and correct
- Warnings must be zero

Linkers:
- ld.bfd (preferred)
- gold (acceptable)

---------------------------------------------------------------------
SECTION 5 — LLVM / CLANG USAGE (DEVELOPMENT / ANALYSIS)
---------------------------------------------------------------------

Primary usage:
- Static analysis
- Sanitizers
- Debugging
- Code quality enforcement

Typical Clang kernel flags:
-ffreestanding
-fno-builtin
-fno-stack-protector
-nostdlib
-Wall
-Wextra
-O2

Strict diagnostics:
-Werror
-Weverything (selectively)

LLVM advantages:
- Better detection of undefined behavior
- More accurate warnings
- Stronger enforcement of C semantics

---------------------------------------------------------------------
SECTION 6 — SANITIZER USAGE (LLVM ONLY)
---------------------------------------------------------------------

Sanitizers are NEVER shipped.
They are used to permanently eliminate bugs.

Common sanitizers:
- UndefinedBehaviorSanitizer
- AddressSanitizer
- MemorySanitizer
- BoundsSanitizer

Typical use cases:
- Detect use-after-free
- Detect null dereference
- Detect integer overflow
- Detect invalid memory access
- Detect stack corruption

Rules:
- Sanitizers are enabled only in debug builds
- Sanitizer failures must be fixed, never ignored
- If Clang sanitizer fails, the code is incorrect

---------------------------------------------------------------------
SECTION 7 — STATIC ANALYSIS (LLVM TOOLING)
---------------------------------------------------------------------

Tools:
- clang --analyze
- clang-tidy

Detects:
- Logic errors
- Missing error checks
- Dead code
- Incorrect assumptions
- Resource leaks

Rules:
- Analysis warnings must be reviewed
- Suppressions must be justified
- Repeated warnings indicate design flaws

---------------------------------------------------------------------
SECTION 8 — CROSS-COMPILER CORRECTNESS RULES
---------------------------------------------------------------------

Rule 1:
If GCC accepts code but Clang rejects it,
the code is WRONG.

Rule 2:
If Clang accepts code but GCC rejects it,
the code must be made portable.

Rule 3:
Compiler-specific behavior must be isolated.

Allowed location:
include/compiler.h

No compiler-specific hacks scattered in code.

---------------------------------------------------------------------
SECTION 9 — INLINE ASSEMBLY RULES (CRITICAL)
---------------------------------------------------------------------

Inline assembly must:
- Use explicit input/output constraints
- Declare all clobbered registers
- Declare memory clobber when memory is touched
- Avoid compiler-specific extensions

LLVM is stricter.
If LLVM rejects inline asm, it is likely unsafe.

---------------------------------------------------------------------
SECTION 10 — LINKER USAGE STRATEGY
---------------------------------------------------------------------

GCC builds:
- ld.bfd (stable, tolerant)
- Preferred for production

LLVM builds:
- lld (fast, strict)
- Preferred for CI and testing

Rule:
Linker warnings are treated as errors.

---------------------------------------------------------------------
SECTION 11 — DEBUG INFORMATION
---------------------------------------------------------------------

Always generate debug symbols.

Debug formats:
- DWARF (preferred)

Rules:
- Debug info must match final binary
- Optimized builds must still be debuggable
- Frame pointers must not be omitted

---------------------------------------------------------------------
SECTION 12 — RECOMMENDED WORKFLOW
---------------------------------------------------------------------

Daily development:
- Clang
- Werror
- Static analysis
- Sanitizers

Pre-merge validation:
- Clang clean build
- GCC clean build
- No warnings allowed

Release build:
- GCC
- Optimized
- No sanitizers
- Debug symbols archived

---------------------------------------------------------------------
SECTION 13 — CONTINUOUS INTEGRATION (CI)
---------------------------------------------------------------------

Minimum CI matrix:
- Clang + sanitizers
- Clang + static analysis
- GCC + optimized build

A change is rejected if:
- Either compiler fails
- Any sanitizer fails
- Any warning appears

---------------------------------------------------------------------
SECTION 14 — WHAT NOT TO DO
---------------------------------------------------------------------

- Do not rely on only one compiler
- Do not ignore Clang warnings
- Do not ship sanitizer builds
- Do not embed compiler hacks in core logic
- Do not trust undefined behavior
- Do not sacrifice correctness for performance

---------------------------------------------------------------------
SECTION 15 — FINAL STABILITY PRINCIPLE
---------------------------------------------------------------------

BSD stability comes from conservative coding.
Beyond-BSD stability comes from compiler diversity.

If:
- GCC agrees
- LLVM agrees
- Sanitizers are clean
- Static analysis is quiet

Then the kernel is structurally correct.
